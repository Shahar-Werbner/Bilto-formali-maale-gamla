# מדריך הפעלה — איך מפתחים את המערכת

**המדריך הזה בשבילך, לא בשביל סשן.** הוא מסביר איך לנהל את הפיתוח מבלי להיות
תלוי בסשן שפתוח כרגע.

שאר המסמכים בתיקייה הזו נכתבו כדי שסשנים יקראו אותם. זה היחיד שנכתב כדי שאתה
תקרא אותו.

---

## הרעיון בשורה אחת

**אתה לא שואל אף סשן "מה הלאה". אתה פותח את `ROADMAP.md` ולוקח את הפריט הראשון
עם ⬜.**

כל השאר במדריך הזה הוא פירוט של המשפט הזה.

## 2. הלולאה היומיומית

### כשאתה רוצה שיתקדם משהו

1. פותח את `ROADMAP.md`.
2. מוצא את **הפריט הראשון עם ⬜** בטבלת הגל הפעיל.
3. פותח סשן חדש, מדביק את **תבנית הביצוע** (סעיף 3), ומחליף את שם הפריט.
4. זהו. הסשן שולף מהריפו את כל השאר.

### מה קורה בזמן שהסשן עובד

הוא מסמן את הפריט 🔨 ודוחף מיד, כדי ששני סשנים לא יבנו את אותו דבר. בסוף הוא
פותח PR, ואם ה-CI ירוק והוא בדק את ההתנהגות — הוא ממזג בעצמו.

### מה אתה עושה אחרי

כלום, בדרך כלל. אם הפריט כלל **מיגרציה או שינוי הרשאות** — הסשן יעצור וישאל
אותך לפני שהוא ממזג.

## 3. שלושת סוגי הסשנים

### א. סשן ביצוע — רוב הזמן

```
קרא קודם CLAUDE.md, ואז docs/ROADMAP.md ו-docs/PROJECT-SUMMARY.md.

**המשימה שלך: <שם הפריט מטבלת הגלים>.**
המפרט המלא ב-docs/ROADMAP.md תחת "<שם הפריט> — המפרט". בצע לפיו.

לפני שאתה כותב קוד: ודא שהפריט ⬜ (אם הוא 🔨 — סשן אחר עליו, עצור ושאל).
סמן אותו 🔨 עם שם הענף שלך ודחוף רק את השינוי הזה. ודא שאתה על ענף חדש
מ-main המעודכן.

אל תיגע ב-prisma/ אם הפריט שלך לא כולל מיגרציה, ואל תוסיף תלות npm בלי לשאול.

בדיקה: typecheck לא מספיק כאן. docs/dev-environment.md מכיל את המתכון
לבדיקה מול Postgres אמיתי ובדפדפן ברוחב טלפון. השתמש בו.

בסיום: עדכן סטטוס ל-✅, כתוב docs/changes/<שם>.md, והוסף ל"הצעות מהשטח"
מה שגילית. PR, ואם CI ירוק והתנהגות נבדקה — מזג.
```

### ב. סשן מיגרציה — כשכמה פריטים צריכים שינוי בסכמה

מריצים אותו **לבד**, ואחריו אפשר להריץ כמה סשנים במקביל.

```
קרא CLAUDE.md ואז docs/ROADMAP.md.

זה סשן מיגרציה יחיד. אתה הבעלים היחיד של prisma/ כרגע, ואף סשן אחר לא רץ.

המשימה: להנחית במיגרציה אחת את כל הסכמה של פריטים <מספרים>.
המפרטים המדויקים ב-ROADMAP תחת "פריט N — המפרט".

אל תבנה את הממשקים — רק את הסכמה, הטיפוסים והבדיקות. המטרה היא שאחריך
הפריטים יוכלו לרוץ במקביל בלי שאף אחד ייגע ב-prisma/.

בדוק מול Postgres מקומי לפי docs/dev-environment.md שהמיגרציה עוברת.
PR, ואם CI ירוק — מזג.
```

### ג. סשן תכנון — כשהתור מתקצר

**מתי**: כשנשארו פחות משני פריטים עם מפרט.

```
קרא CLAUDE.md, docs/ROADMAP.md ו-docs/PROJECT-SUMMARY.md.

זה סשן תכנון — אל תיגע בקוד.

עבור על הפריטים ב-ROADMAP שאין להם עדיין מפרט, ועל "הצעות מהשטח".
כתוב מפרט ברמת ביצוע לשלושת הפריטים הבאים בתור, באותו פורמט כמו
"פריט 1 — המפרט המלא": מודל הנתונים המדויק, מה משתנה בקוד הקיים,
והבדיקות שחייבות ללוות.

אם משהו בסדר העדיפויות כבר לא נכון לאור מה שנבנה — תגיד לי, אל תשנה לבד.
PR, ואם CI ירוק — מזג.
```

## 4. מה אתה מחליט ומה סשן מחליט

| סשן מחליט לבד          | אתה מחליט                             |
| ---------------------- | ------------------------------------- |
| איך לממש את המפרט      | **מה נבנה ובאיזה סדר**                |
| שמות, מבנה קוד, בדיקות | מיגרציה **הרסנית** (מחיקת עמודה/טבלה) |
| למזג PR שה-CI שלו ירוק | שינוי **הרשאות**                      |
| להציע פריטים חדשים     | הוספת **תלות npm**                    |
|                        | כל דבר **שקשה לבטל**                  |

**סשן מציע, אתה מחליט.** הצעות נכנסות ל"הצעות מהשטח" ב-ROADMAP; אתה מקדם או
מוחק. זה מה שמונע מהמערכת להיבנות לפי מה שמעניין טכנית במקום לפי מה שאתה צריך.

## 5. מקביליות — מתי אפשר וכמה

**הכלל היחיד שחייב להישמר: בעלים אחד ל-`prisma/`.**

מיגרציות רצות אוטומטית בכל פריסה של Vercel — **כולל ב-preview של כל PR**. שני
ענפים עם מיגרציות מחילים אותן על אותו בסיס נתונים, בלי שמוזג כלום. זה לא נשבר
ב-merge, זה נשבר בפרודקשן.

לכן:

- פריט שדורש מיגרציה → **רץ לבד**.
- כמה פריטים שדורשים מיגרציה → **סשן מיגרציה אחד קודם**, ואז הם במקביל.
- **שניים-שלושה סשנים במקביל זו התקרה המעשית** לריפו בגודל הזה. מעבר לזה זמן
  האינטגרציה אוכל את הרווח.

## 7. אחרי מיזוג — מה לבדוק

רוב המיזוגים לא דורשים ממך כלום. שניים כן:

- **לאפס את סיסמת ה-DB של Neon** — נחשפה בצ'אט בזמן ההקמה.

  בסיס נתונים כמו הפרודקשן. פירוט ב-`ROADMAP.md`.
