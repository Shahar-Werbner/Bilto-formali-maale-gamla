# תוכנית בנייה ועבודה במקביל

מסמך העבודה של הפרויקט. מי שנכנס לפתח — **קורא את זה קודם**, ואז את
`docs/PROJECT-SUMMARY.md` (מצב המערכת) ואת `README.md`.

**המערכת עדיין לא בשימוש** — בבנייה לקראת יום פעילות ראשון. אין נתוני אמת
להגן עליהם, ולכן **שינוי מבנה הוא זול עכשיו ויקר אחר כך**; עדיף לתקן את הצורה
מאשר לשמר את מה שקיים.

עם זאת, כל שינוי שנדחף ל-`main` עדיין נפרס דרך Vercel, כולל מיגרציות
(`prisma migrate deploy` רץ ב-build, **גם ב-preview של PR**). זה קובע את רוב
הכללים למטה.

### גל 0 — תשתית (סשן אחד בלבד, לא במקביל)

הדברים שנוגעים ב**שטח המשותף** של הקוד. חייבים לנחות לפני שמתחילים לעבוד במקביל.

1. **הרשאות: `admin` מול `staff`.** היום כל מי שיש לו את קוד הצוות יכול למחוק
   אירוע שלם או ילד עם כל ההיסטוריה שלו. `role` כבר קיים ב-JWT ובסשן — צריך
   לאכוף אותו: `requireRole("admin")` לפני כל DELETE, מסך ניהול משתמשים,
   והרשמה שמנפיקה `staff` בלבד.
2. **מחיקה רכה (`deletedAt`)** לאירוע ולילד, וסינון בכל שאילתה. בשימוש יומיומי
   מהטלפון, מחיקה בטעות היא שאלה של מתי, לא אם.
3. **מיגרציה אחת** שמכסה את כל מה שהמסלולים המקבילים צריכים, כדי שאף אחד מהם
   לא ייגע ב-`prisma/`.
4. **אינדקסים**: `EventAttendance.participantId`, `EventDay.date`.
5. **כל תלות npm חדשה** שהמסלולים צריכים — נוחתת כאן, בבת אחת.

**✅ גל 0 הושלם.** מה שנחת בפועל:

- `admin` מול `staff`, נאכף בשרת. מחיקת אירוע, מחיקת ילד, שחזור ושינוי תפקיד —
  מנהל/ת בלבד. **התפקיד נקרא מה-DB ולא מה-JWT**: אחרת הורדה מתפקיד לא הייתה
  נכנסת לתוקף עד שהמשתמש היה מתחבר שוב, ימים אחר כך.
- **מחיקה רכה** לאירוע ולילד + מסך `/admin` עם סל מחזור לשחזור, וסינון
  `deletedAt` בכל נתיב קריאה במערכת.
- **מיגרציה `add_roles_soft_delete_contacts`** — כולל שלב data migration שמקדם
  את המשתמש הוותיק ביותר ל-admin. בלעדיו הפרודקשן היה נשאר בלי אף מנהל/ת, בלי
  דרך למנות אחד.
- שדות קשר על `Participant` (`parentName`, `parentPhone`, `phone`) — מוכנים
  למסלול A.
- הגנות: אי אפשר להוריד לעצמך הרשאות, ואי אפשר להשאיר את המערכת בלי מנהל/ת.

**החלטה: לא נאגר מידע רפואי/אלרגיות** בשלב הזה. הסכמה בנויה כך שאפשר להוסיף

### פריט 1 — המפרט המלא (✅ נבנה)

**נבנה כמפורט כאן**, עם שתי סטיות שמתועדות ב-`docs/changes/wave3-item1-cyclic-schedule.md`:
נוספה תקרת טווח כ-`MAX_EVENT_RANGE_DAYS = 400` שמחזירה רשימה ריקה (דחייה ב-API,
לא חיתוך), ונקבע ש-PATCH מרענן שעות של ימים קיימים **רק** אם הן עדיין זהות
למה שהתבנית הישנה ייצרה. המפרט נשאר כאן כתיעוד של ההחלטה.

**הבעיה**: `Event` מחזיק טווח תאריכים רציף עם checkbox לשישי/שבת. אי אפשר לבטא
"כל שלישי וכל שישי לאורך שנה". כדי להקים שנה צריך ~80 אירועים נפרדים, או אירוע
אחד שמייצר גם את כל ימי א׳-ב׳-ד׳-ה׳. שניהם לא שמישים.

**בנוסף**: לכל מפגש צריכות להיות שעות התחלה וסיום (ג׳ = 3 שעות, ו׳ = 4). זה לא
קוסמטי — **שעות הצוות (פריט 6) נגזרות מזה**. בלי זה מעקב השעות יהיה הקלדה ידנית.

**המודל המוצע** (נבחן ונבדק מול הקוד הקיים):

```prisma
model Event {
  kind             String @default("camp")  // "recurring" | "camp"
  startDate, endDate                        // כמו היום
  includeFriday, includeSaturday            // רלוונטי ל-camp בלבד
  defaultStartTime String?                  // "09:00" — שעות של camp
  defaultEndTime   String?
  weekdays         EventWeekday[]           // רלוונטי ל-recurring בלבד
}

model EventWeekday {
  id        String @id @default(cuid())
  eventId   String
  event     Event  @relation(fields: [eventId], references: [id], onDelete: Cascade)
  weekday   Int    // 0=ראשון … 6=שבת
  startTime String // "16:00"
  endTime   String // "19:00"
  @@unique([eventId, weekday])
}

model EventDay {
  startTime String?  // מולא מהתבנית, וניתן לדריסה ליום בודד
  endTime   String?
}
```

**למה טבלה ולא מערך**: כל יום בשבוע צריך שעות משלו. `weekdays Int[]` לא יכול
לבטא "ג׳ 16:00–19:00, ו׳ 09:00–13:00". השעות על `EventDay` הן עותק קונקרטי, כדי
שאפשר יהיה לשנות יום בודד בלי לשנות את התבנית.

**לוגיקת הייצור** (`src/lib/events.ts`) — להחליף את `generateEventDates`:

```ts
generateEventDays({ startDate, endDate, kind, weekdays?, includeFriday?,
                    includeSaturday?, defaultStartTime?, defaultEndTime? })
  → Array<{ date, startTime, endTime }>
```

- `recurring` → רק ימים שתואמים ל-`weekdays`, עם השעות של אותו יום בשבוע.
- `camp` → כל יום בטווח, מדלג שישי/שבת אלא אם נכללו, עם שעות ברירת המחדל.
- `recurring` בלי אף יום בשבוע → רשימה ריקה (שה-API ידחה), לא "כל יום".
- **תקרת טווח ~400 ימים** ודחייה מעליה. שנת לימודים היא ~300 ימים; טווח גדול
  יותר הוא כמעט תמיד טעות הקלדה, וייצור ממנו יוצר אלפי שורות.
- להוסיף `hoursBetween(startTime, endTime)` — מחזיר 0 לזוג חסר או הפוך, כדי
  ששורה שגויה לא תוסיף שעות בשקט לחודש של מישהו. פריט 6 יסתמך על זה.

**מה עוד צריך להתעדכן**: `POST/PATCH /api/events` (לקבל kind ותבנית), טופס
אירוע חדש, `EventSettings`, והצגת השעות בדף היום. `PATCH` כבר יודע להוסיף ימים
תוספתית ולא למחוק ימים עם נתונים — לשמור על ההתנהגות הזו.

**בדיקות שחייבות להיות**: שנה של ג׳+ו׳ מייצרת רק את הימים הנכונים עם השעות
הנכונות; קייטנה נשארת כמו שהייתה; `recurring` בלי ימים מחזיר ריק; טווח ארוך
מדי נדחה; `hoursBetween` על זוג הפוך/חסר.

### ✅ נחת — מחיקה רכה לקבוצות (PR #13)

`prisma/` **שוחרר** עם המיזוג. **אל תחזיר את מחיקת הקבוצה למחיקה קשה** — היא
מחקה גם את שיבוצי הקבוצות של מפגשי העבר.

**מחיקת קבוצה יושבת על היכולת `group:delete`** שנוספה לטבלה של פריט 4 —
מנהל/ת בלבד, בעוד `group:edit` (שינוי שם) נשאר פתוח לצוות בוגר. הפירוט והנימוק
ב-`docs/changes/group-soft-delete.md`.

**ההחלטה של בעל הפרויקט (19.09): שומרים את שני סוגי הקבוצות.**
קבוצות קבועות (`Participant ↔ Group`) **וגם** קבוצות למפגש
(`DayGroupAssignment`) — לא מוחקים אף אחד מהם. זה מבטל את ההמלצה שבמפרט של
פריט 3 להסיר את החברות הגלובלית; **המפרט למטה עודכן בהתאם.**

**מה שהתברר בבדיקה מול DB חי**: מחיקת קבוצה עובדת, הילדים והנוכחות שורדים —
אבל היא **מוחקת את התיעוד של מי היה בקבוצה בכל מפגש בעבר**. מפגש של 12.3 שבו
היו שלושה ילדים מוצג אחר כך עם אחד, כאילו לא היו שם. מחיקה בהווה משכתבת את העבר.
זה לא הפריע כשקבוצה הייתה רק תווית; עכשיו היא רשומה היסטורית.

לכן: **`Group.deletedAt`** — אותה מחיקה רכה של `Event` ו-`Participant`. הכפתור
מתנהג בדיוק כמו היום, הקבוצה נעלמת מכל המסכים, מפגשי העבר ממשיכים להציג אותה,
ואפשר לשחזר מ-`/admin`. בנוסף, המחיקה עוברת ל**מנהל/ת בלבד** דרך יכולת חדשה
`group:delete` בטבלת היכולות של פריט 4 — היא הייתה `requireSession`, היוצאת דופן
היחידה מול מחיקת ילד ואירוע. **`group:edit` (שינוי שם) נשאר פתוח לצוות בוגר**;
מחיקה היא לא עריכה, כי היא מסתירה שם שמפגשי עבר מפנים אליו.

### פריט 2 — שחרור ואיסוף: המפרט

**החמור ביותר בגל הזה.** ילדים בני 6–9; מי מורשה לקחת אותם הביתה זה לא שדה נתונים.

> ✅ **המודלים האלה כבר בסכמה ובבסיס הנתונים.** אל תיצור מיגרציה בשבילם.
> הבלוק למטה הוא **מה שתוכנן**, וההגדרה בפועל — עם המפתחות הזרים, האינדקסים
> וה-cascade — נמצאת ב-`prisma/schema.prisma`. **היא מקור האמת, לא הבלוק הזה.**

```prisma
model PickupAuthorization {           // מי מורשה לאסוף את הילד/ה — קבוע
  id            String @id @default(cuid())
  participantId String
  participant   Participant @relation(fields: [participantId], references: [id], onDelete: Cascade)
  name          String
  phone         String?
  relation      String?               // "אמא", "סבתא", "שכנה"
  createdAt     DateTime @default(now())
  @@index([participantId])
}

model Dismissal {                     // מה קרה בפועל בסוף מפגש
  id             String @id @default(cuid())
  eventDayId     String
  participantId  String
  method         String               // "alone" | "escort"
  pickedUpByName String?              // מי אסף בפועל
  at             DateTime?
  note           String?              // שינוי חד-פעמי: "היום סבתא"
  markedByUserId String?
  @@unique([eventDayId, participantId])
}
```

ועל `Participant`: `defaultDismissal String @default("escort")` — ההוראה הקבועה.
**גם היא כבר קיימת.**

**ברירת מחדל בטוחה, וזה העיקר**: ילד בלי הוראה מפורשת = **מחכה למבוגר**. לא
"מניחים שהולך לבד". ברירת המחדל של העמודה היא `"escort"` בכוונה.

**מסך שחרור**: רשימת הילדים של היום — מי הולך לבד, מי מחכה, מי כבר נאסף ועל ידי
מי. **סימון יציאה, לא רק כניסה.** זה המקביל לנוכחות בסוף היום.

**הרשאות**: עריכת מורשי איסוף = `admin` או מדריך בוגר בלבד, **לא מדריך נוער**.
תפקיד `youth` כבר קיים ונאכף (פריט 4 שלב א׳), אז זה `requireCapability` ולא
`admin` בלבד — צריך יכולת חדשה, למשל `dismissal:authorize`.

**מי רשאי לסמן שחרור — הוחלט 19.09:**

> **מדריך נוער רשאי לסמן שחרור התואם את רשימת מורשי האיסוף. כל חריגה מחייבת
> מדריך בוגר או מנהל/ת.**

חריגה = שם שאינו ברשימה, או שינוי חד-פעמי (`Dismissal.note`).

הנימוק: רוב הצוות הוא מדריכי נוער. לחייב בוגר על **כל** שחרור פירושו שהכלל
ייעקף בשטח בסוף היום הראשון, וכלל שנעקף גרוע מכלל שאין. לכן השער יושב על
**המקרה המסוכן בלבד** — מישהו שלא ברשימה בא לקחת ילד/ה בן 6 — ולא על השגרה.
מדריך נוער שנתקל בחריגה רואה מסך שאומר "צריך אישור של בוגר", לא כפתור שנכשל.

**בדיקות חובה**: ילד בלי הוראה מופיע כ"מחכה"; שינוי חד-פעמי לא דורס את ההוראה
הקבועה; אי אפשר לסמן שחרור לילד שלא באירוע; **`youth` מצליח לסמן שחרור לשם
שברשימה ומקבל 403 על שם שאינו ברשימה ועל `note` חד-פעמי**.

### פריט 3 — קבוצות ברמת המפגש: המפרט

**הוחלט: הקבוצות משתנות בין מפגש למפגש.**

> ✅ **המודלים האלה כבר בסכמה ובבסיס הנתונים.** אל תיצור מיגרציה בשבילם.
> הבלוק למטה הוא **מה שתוכנן**, וההגדרה בפועל — עם המפתחות הזרים, האינדקסים
> וה-cascade — נמצאת ב-`prisma/schema.prisma`. **היא מקור האמת, לא הבלוק הזה.**

```prisma
model DayGroupAssignment {
  id            String @id @default(cuid())
  eventDayId    String
  participantId String
  groupId       String
  @@unique([eventDayId, participantId])   // ילד/ה בקבוצה אחת ביום נתון
  @@index([eventDayId])
}
```

`Group` נשאר **שם לשימוש חוזר** (א׳, ב׳, "האריות"), ו-`ActivitySlot.groupId`
ממשיך להצביע עליו — כך שסלוט מכוון לקבוצה באותו יום.

> ⚠️ **`Group` עבר למחיקה רכה** (`Group.deletedAt`, PR #13). כל שאילתה שמציגה
> קבוצות או פותרת אותן חייבת לסנן — יש `liveGroup(id)` ב-`event-scope.ts`.
> **אל תחזיר את מחיקת הקבוצה למחיקה קשה**: היא מחקה גם את שיבוצי הקבוצות של
> מפגשי העבר, כך שמפגש ישן הוצג אחר כך בלי חלק מהילדים.

**החברות הגלובלית הקיימת** (`Participant ↔ Group`) — **נשארת. אל תסיר אותה.**

> ⚠️ **המפרט הזה נכתב במקור עם המלצה הפוכה** ("להסיר את החברות הגלובלית").
> **בעל הפרויקט החליט אחרת ב-19.09: רוצים את שני הסוגים.** הפסקה הוחלפה. אם
> ראית את הגרסה הישנה במקום אחר — היא לא תקפה.

כלומר שני דברים שונים, ושניהם נשמרים:

| סוג                                   | מה זה                                                       | לאן זה נכתב            |
| ------------------------------------- | ----------------------------------------------------------- | ---------------------- |
| **קבוצה קבועה** (`Participant ↔ Group`) | "יעל שייכת ל'אריות' השנה" — החלוקה שלא משתנה כל שבוע        | `Group.participants`   |
| **קבוצה למפגש** (`DayGroupAssignment`) | "ביום שלישי הזה יעל הייתה ב'נמרים'" — מה שקרה בפועל באותו יום | `DayGroupAssignment`   |

**מקור האמת ליום נתון הוא תמיד `DayGroupAssignment`.** החברות הקבועה היא
**ברירת מחדל שממלאים ממנה**, לא מה שמוצג כשיבוץ. מפגש בלי שיבוצים לא אומר
"כולם בקבוצות הקבועות שלהם" — הוא אומר שעוד לא חילקו.

**מה שצריך להיבנות מעליה**: כפתור מילוי מקדים למפגש, עם שלוש אפשרויות —
"לפי הקבוצות הקבועות", "העתק מהמפגש הקודם", "חלק לפי כיתה". זה הופך את החלוקה
השבועית מעבודה ידנית לתיקון של כמה ילדים.

`/api/events/[id]/participants/bulk` ("הוספת קבוצה שלמה לאירוע") ממשיך לעבוד
כמו שהוא ונשען על החברות הקבועה — **לא צריך לגעת בו.**

**בדיקות**: מילוי מקדים משלוש המקורות; ילד שלא היה במפגש הקודם נשאר בלי שיבוץ;
שינוי שיבוץ ביום אחד לא נוגע במפגשים אחרים ולא בחברות הקבועה; מפגש בלי שיבוצים
מוצג כ"טרם חולק" ולא כקבוצות הקבועות.

### פריט 4 — שיבוץ צוות ותפקיד youth: המפרט

> ✅ **המודלים האלה כבר בסכמה ובבסיס הנתונים.** אל תיצור מיגרציה בשבילם.
> הבלוק למטה הוא **מה שתוכנן**, וההגדרה בפועל — עם המפתחות הזרים, האינדקסים
> וה-cascade — נמצאת ב-`prisma/schema.prisma`. **היא מקור האמת, לא הבלוק הזה.**

```prisma
model Shift {
  id         String @id @default(cuid())
  userId     String
  eventDayId String
  startTime  String?          // ברירת מחדל: שעות המפגש
  endTime    String?
  role       String?          // "אחראי", "מדריך קבוצה"
  note       String?
  @@unique([userId, eventDayId])
  @@index([eventDayId])
}
```

**תפקיד שלישי: `youth`** — ✅ **נבנה ונמזג** (שלב א׳ למטה). הוא כבר ב-`ROLES`,
עם טבלת יכולות ואכיפה על כל הנתיבים. **אין מה להוסיף ל-`roles.ts` בשביל זה.**

מה ששלב ב׳ עוד צריך מ-`roles.ts`: `shift:view:own`, `shift:view:all`
ו-`shift:assign` כבר מוצהרות. חסרה **`shift:availability`** — מדריך נוער מסמן
זמינות אבל לא משבץ את עצמו (הוכרע 19.09).

**התרעת יחס**: לכל מפגש — כמה ילדים צפויים מול כמה מדריכים משובצים, והתרעה
כשהיחס נמוך מסף שניתן להגדרה. זו השאלה היומיומית ("מי מגיע בשלישי, וחסר לנו
מישהו?"), לא הדוח החודשי.

**בדיקות**: שעות ברירת מחדל מגיעות מהמפגש; דריסה ידנית גוברת; `youth` מקבל 403
על נתיבים שאינם שלו.

#### ✅ שלב א׳ הושלם — התפקיד וההרשאות

**לא נגע ב-`prisma/`** — `role` הוא `String`.

הסדר כאן הוא לא קוסמטי. היום **19 נתיבים** משתמשים ב-`requireSession`, שפירושו
"כל מי שמחובר". להוסיף את `youth` ל-`ROLES` לפני האכיפה היה נותן לו את כל 19
בבת אחת — כולל ייבוא רשימה ופרטי קשר של הורים. לכן: **קודם מנגנון, אחר כך
תפקיד**, ובאותו PR.

**מה שנחת**: `youth` ב-`ROLES`, טבלת יכולות ב-`roles.ts`, `requireCapability()`
על כל 19 הנתיבים שהיו על `requireSession`, הגנת שדה על פרטי הקשר (לא נשלפים
מה-DB כלל ללא `roster:contacts`), ובדיקה שסורקת כל נתיב ונכשלת על אחד שלא מצהיר
יכולת. פירוט מלא, כולל טבלת 19 פעולות × 3 תפקידים מול DB חי:
`docs/changes/wave3-item4-youth-role.md`.

**שלב ב׳ — לא התחיל.** שיבוץ בפועל + התרעת יחס על `Event.maxChildrenPerStaff`
(העמודה כבר קיימת, **אין צורך במיגרציה**). הפריט מסומן ⏸ ולא 🔨: שלב א׳ נמזג,
ואף אחד לא עובד על שלב ב׳ כרגע.

**לולאת האישור — ✅ השדות נחתו** (`20260919164346_add_activity_slot_approval`):
`ActivitySlot.status` (`@default("approved")`), `approvedByUserId`, `approvedAt`.

כלומר **החסם הוסר**. `youth` עדיין מקבל צפייה בלבד בלוז, כי `schedule:edit`
נשללה ממנו בשלב א׳ — וזו הייתה רצפה זמנית בדיוק עד לרגע הזה. שלב ב׳ יכול
עכשיו לפתוח לו תכנון: יכולת `schedule:propose` שכותבת סלוט עם
`status: "pending"`, ו-`schedule:approve` לבוגר שמאשר. **אין צורך במיגרציה.**

#### הוכרע 19.09 — שלוש ההחלטות שהיו פתוחות

**1. שיבוץ עצמי: לא. מדריך נוער מסמן זמינות; השיבוץ נשאר אצל בוגר.**
היכולת `shift:assign` נשארת ל-`staff` ול-`admin` בלבד, ותתווסף `shift:availability`
ל-`youth`. הנימוק: אם אפשר לשבץ את עצמך, **התרעת היחס ניתנת לעקיפה** — מי שנרשם
למשמרת "קלה" משאיר חור במשמרת אחרת, וההתרעה תראה מספרים תקינים. זמינות נותנת
לבוגר את אותו מידע בלי להעביר אליו את ההחלטה.

**2. שכר: שעות נכנסות למערכת, כסף לא.**
`Shift` שומר שעות; **אין עמודת תעריף ואין סכומים.** דוח השעות (פריט 6) מייצא
שעות, והשכר מחושב במקום שבו מחושב שכר. הנימוק: תעריפים הם מחלקת נתונים חדשה
לגמרי, והיא נוגעת בקטינים — עדיף לא להחזיק אותה באפליקציה שנפתחת מהטלפון של
בן 15. (ובנוסף: העסקת נוער בישראל מוסדרת בחוק, כולל מגבלות שעות. מי שאחראי
בארגון צריך לראות את זה לפני שאוגרים תעריפים — זו לא הערה משפטית, זו סיבה לא
להיכנס לשם בלי החלטה מודעת.)

**3. שחרור: מדריך נוער מסמן שחרור תואם-רשימה; חריגה מחייבת בוגר.**
המפרט המלא בפריט 2 למעלה.

**✅ לולאת האישור כבר לא חסומה.** שלוש העמודות על `ActivitySlot` נחתו
(`20260919164346_add_activity_slot_approval`): `status` עם `@default("approved")`,
`approvedByUserId`, `approvedAt`, ואינדקס על `status` לתור הבדיקה.

**מה שנשאר לפריט 4 שלב ב׳** — הכול בקוד, בלי מיגרציה:

1. יכולת `schedule:propose` ל-`youth` (ו-`schedule:approve` לבוגר), ב-`roles.ts`.
2. נתיב הכתיבה ללוז כותב `status: "pending"` כשהכותב אינו בעל `schedule:edit` —
   **ברירת המחדל בעמודה היא `approved` בכוונה**, כי מי שרשאי לערוך, האישור שלו
   גלום ביצירה. רק מי שצריך אישור נכתב כ-`pending`, במפורש.
3. מסך: מדריך נוער רואה "נשלח לאישור" במקום כפתור שנכשל; בוגר רואה תור בדיקה
   ליום (`where: { status: "pending" }`).
4. אישור כותב את השלושה יחד: `status`, `approvedByUserId`, `approvedAt`.

### פריט 7 — מאגר פעילויות: המפרט

**למה זה שווה**: מדריכי נוער מתחלפים, והידע הולך איתם. מאגר הופך ניסיון אישי

model Activity {

### פריט 8 — טופס הרשמה: המפרט

**העיקרון: לא בונים בונה-טפסים.** ברגע שהשדות שרירותיים, התשובות נשמרות כ-blob

  טבלת תאריכים ידנית (זול, צריך תחזוקה שנתית) או ספרייה (תלות npm — נוחתת בגל 0).

## חלק ב׳ — איך עובדים במקביל בלי להתנגש

### ⚠️ סכנה שהתגלתה בפועל: preview של Vercel מריץ מיגרציות

`build` הוא `prisma generate && prisma migrate deploy && next build`, ו-Vercel
מריץ אותו **גם ל-preview של כל PR**. כלומר: הרגע שנפתח PR עם מיגרציה, היא מוחלת
על בסיס הנתונים שאליו ה-preview מוגדר — **לפני שמישהו סקר או מיזג**.

אם משתני הסביבה ב-Vercel מוגדרים ל-"All Environments" (וזו ברירת המחדל כשמוסיפים
אותם בלי לבחור סביבה), זה אומר שה-preview מריץ מיגרציות **על הפרודקשן**.

בדיקה ב-Neon SQL Editor:

```sql
SELECT column_name FROM information_schema.columns
WHERE table_name = 'Participant' AND column_name = 'deletedAt';
```

אם השורה קיימת — המיגרציה כבר הוחלה על הפרודקשן מתוך preview.

**למה זה קריטי דווקא כאן**: התוכנית הזו מריצה כמה מסלולים במקביל. אם שניים מהם
יחזיקו מיגרציות, שני ה-preview שלהם יחילו אותן על אותו DB, בסדר אקראי, בלי
שאף אחד מיזג כלום. זה מחמיר את הכלל של "בעלים אחד ל-`prisma/`" מהמלצה לחובה.

**שתי דרכים לתקן** (החלטה של בעל הפרויקט, לא שינוי קוד חד-צדדי):

1. **DB נפרד ל-preview** — Neon תומך ב-branching. ב-Vercel מגדירים
   `DATABASE_URL`/`DIRECT_URL` ל-Preview בנפרד מ-Production. זו הדרך הנקייה:
   ה-preview נשאר שימושי, והפרודקשן מוגן.
2. **להריץ מיגרציות רק בפרודקשן** — להתנות את `migrate deploy` ב-`VERCEL_ENV`.
   פשוט יותר, אבל preview עם סכמה חדשה פשוט יישבר.

### למה החלוקה המתבקשת נכשלת

"סשן לכל פיצ'ר" נשמע נכון ונשבר כאן, כי בריפו של ~35 קבצי מקור כמעט כל פיצ'ר
נוגע באותם חמישה מקומות:

| הקובץ                                         | מי רוצה לגעת בו     | מה קורה בהתנגשות                                                                                                                       |
| --------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `prisma/schema.prisma` + `prisma/migrations/` | כל פיצ'ר עם נתונים  | **הכי מסוכן.** שתי שרשראות מיגרציה מקבילות לא נשברות ב-merge אלא ב-**deploy** — `migrate deploy` רץ ב-build של Vercel ונכשל על פרודקשן |
| `package-lock.json`                           | כל מי שמוסיף ספרייה | קובץ של 285KB. התנגשות בו היא בפועל בלתי ניתנת למיזוג                                                                                  |
| `src/components/AppHeader.tsx`                | כל מסך חדש          | התנגשות קטנה אבל מובטחת                                                                                                                |

| `README.md`, `docs/PROJECT-SUMMARY.md`        | כולם                | התנגשות בכל סבב                                                                                                                        |

### הפתרון: לחלק לפי **בעלות על קבצים**, לא לפי פיצ'ר

1. **גל 0 קודם, לבד.** כל מה שנוגע בשטח המשותף נוחת פעם אחת. אחרי זה המסלולים
   נוגעים כמעט רק בקבצים חדשים.
2. **עמודי stub מראש.** גל 0 יוצר את המסך הריק ואת הכניסה בניווט לכל מסך עתידי.
   ככה מסלול שבונה מסך חדש **לא נוגע ב-`AppHeader`** — רק ממלא קובץ שכבר קיים
   ורק הוא נוגע בו. זה הופך את ההתנגשות הכי מובטחת לאפס.
3. **בעלות מוצהרת על נתיבים.** לכל מסלול יש רשימת נתיבים משלו (טבלה למטה).
   מחוץ לרשימה — לא נוגעים, גם אם רואים משהו שכדאי לתקן. פותחים על זה שורה
   ב-`docs/changes/<מסלול>.md` ונטפל בנפרד.

### הכללים

1. **בעלות על `prisma/`**: רק סשן הסכמה יוצר מיגרציות. אף מסלול מקבילי לא נוגע
   ב-`schema.prisma`. צריך שדה שלא קיים? עוצרים ומבקשים — הוא ינחת ואז תעשו rebase.
2. **אין תלויות npm חדשות במסלול מקבילי.** מצהירים; זה נוחת בגל 0.
3. **לא נוגעים ב-chrome המשותף**: `AppHeader.tsx`, `layout.tsx`, `globals.css`,
   `middleware.ts`, `auth.ts`, `auth.config.ts`, `src/lib/api-error.ts`.
4. **לא עורכים `README.md` ולא `PROJECT-SUMMARY.md`.** כל מסלול כותב
   `docs/changes/<מסלול>.md` (קובץ חדש — אפס התנגשות), והם ימוזגו בסוף.
5. **אין ריפקטור או עיצוב מחדש דרך אגב.** סבב פורמט הופך diff של 3 שורות
   להתנגשות של 300.
6. **ענף לכל מסלול, כולם מאותו base**, מיזוג לפי הסדר שבטבלה, ו-rebase אחרי
   כל מיזוג.
7. **לפני push**: `npm test && npm run lint && npm run typecheck` ירוקים. שלושתם.
   CI מריץ את אותם שלושה על כל PR, אבל עדיף לגלות לפני.
8. **בדיקה אמיתית, לא רק typecheck.** המתכון המלא ב-`docs/dev-environment.md`.
